# Hiking Photo Analysis

Analyze a hiking photo and produce a concise, structured visual summary without bloating conversation context, augmented with verified geographic, botanical, and geological details visible in the frame.

## Helper Scripts

All CLI flags and output JSON schemas for `scripts/` are documented below so you **never** need to run `--help` or inspect script source code:

- **`scripts/extract_metadata.py`**: Runs ExifTool (with directory-level batch caching), queries USGS 3DEP ground elevation and administrative boundaries, detects stitched panoramas, and computes chronologically preceding/succeeding hike travel vectors in one shot:
  ```bash
  python C:\Users\Tilman\.gemini\config\skills\photo-analysis\scripts\extract_metadata.py "<photo_path>" --ref-elev-ft "Trailhead:5267" --ref-elev-ft "High Point:7990"
  ```
  - **CLI Flags**: `<photo_path>`, `--ref-elev-ft "Label:ElevFt"` (repeatable).
  - **Output JSON Keys**:
    - Core & coordinates: `photo_path`, `date_time`, `gps_dms`, `lat`, `lon`, `missing_gps_guidance` (emitted when `lat`/`lon` is `null` to warn when `prev_photo` is `null` or `elapsed_time_min > 15` to read `post.md` before running `geo_tools.py`)
    - Elevation: `ground_elevation_ft`, `ground_elevation_m`, `exif_elevation_ft`, `exif_elevation_m`, `elevation_formatted`, `elevation_deltas`
    - Camera, lens & exposure: `camera_model`, `lens_model`, `focal_length_mm`, `focal_length_35mm`, `estimated_single_frame_hfov_deg`, `exposure_time`, `f_number`, `iso`, `camera_spec_formatted`, `image_width`, `image_height`
    - Panorama detection: `is_stitched_panorama_candidate`, `panorama_guidance`
    - Neighbor & trajectory vectors: `prev_photo`, `next_photo` (skipping stationary burst/pano frames `<4.0 m`; each has `filename`, `date_time`, `lat`, `lon`, `elevation_ft`, `elevation_m`, `elevation_change_ft`, `elevation_change_m`, noise-aware `trail_gradient`, `elapsed_time_min`, `travel_vector_from_prev` / `travel_vector_to_next`), `prev_hike_stops`, `next_hike_stops` (up to 3 preceding and 3 succeeding stops separated by `>= 25 m` or `>= 45 s`)

  - Never run `exiftool.exe` separately after `extract_metadata.py`. *Fallback* (only if `extract_metadata.py` cannot run): `exiftool.exe -d "%Y-%m-%d %H:%M:%S" -DateTimeOriginal -GPSPosition -c "%d°%d'%.2f\"" -GPSLatitude# -GPSLongitude# -GPSAltitude# -FocalLength# -FocalLengthIn35mmFormat# "<photo_path>"`

## Analysis Steps

1. **Location, Date & Time**:
   - Extract timestamp, GPS coordinates, and `admin_boundaries` via `extract_metadata.py`. Identify the wilderness area, national forest, state/national park, mountain range, and specific trail (checking near trail junctions whether the route branched onto a secondary trail).
   - If EXIF GPS is missing (`lat: null, lon: null`), note `[Not available in EXIF]`, follow the Stage 1 Missing-EXIF-GPS exception below, and keep your estimated `(lat, lon)` fixed across `geo_tools.py` calls rather than jittering by `0.01°` (which busts the `0.01°` grid cache).

2. **Elevation & Authoritative Benchmark Precedence**:
   - Retrieve official USGS 3DEP ground elevation and benchmark deltas via `extract_metadata.py` (`--ref-elev-ft "Label:ElevFt"`). Report elevation in plain-text dual units: `XXX ft / YYY m` (never bare `ft` or parentheses `ft (m)`), with relative context when relevant (`~XXX ft / YYY m above trailhead`).
   - **Authoritative `--ref-elev-ft` & Stage 2 `post.md` Elevation Reconciliation (`DEM-Smoothing Rule`)**:
     1. **`--ref-elev-ft` Precedence**: When a landmark elevation is provided via `--ref-elev-ft` (e.g., `Kearsarge Pass:11814`), use that exact benchmark (`11,814 ft / 3,601 m`) consistently across `Elevation`, `Identified Natural Features`, and `Suggested Caption`—never mix it with the smoothed 3DEP DEM / GNIS centroid sample (`11,711 ft / 3,569 m`).
     2. **Physical DEM-Smoothing Rule vs. `post.md`**: Because 10m/30m 3DEP DEM rasters average terrain across a grid cell and GNIS centroids often sit slightly off the summit cairn, DEM samples for sharp peaks systematically read **`20–130 ft` lower** than true USGS quadrangle spot elevations—never higher:
        - **(a) `post.md` Higher by `+10 to +150 ft` $\rightarrow$ Adopt `post.md` Elevation**: If `post.md` cites a summit/pass elevation `10–150 ft` higher than the 3DEP DEM sample (e.g., `Deerhorn Mountain (13,265 ft)` vs. `13,139 ft` DEM), `post.md` reflects the true USGS benchmark—adopt `13,265 ft / 4,043 m` in `Identified Natural Features` and `Suggested Caption`.
        - **(b) `post.md` Lower Than DEM or Off by `> 150 ft` $\rightarrow$ Keep USGS/DEM Elevation & Flag Discrepancy**: A true summit cannot be lower than its smoothed DEM average. If `post.md` cites an elevation lower than the DEM/GNIS sample (e.g., `West Vidette (12,241 ft)` vs. `12,518 ft / 3,815 m` DEM/USGS) or differs by `> 150 ft`, keep the USGS/DEM elevation in your feature list and explicitly flag the discrepancy in `Suggested Draft Placement`.
     3. **No Example Copying or Dual-Elevation Header Hedging**: Only adopt a higher USGS/topographic benchmark elevation when that specific feature's elevation is explicitly cited in the current hike's `post.md` or `--ref-elev-ft` flags—**never** copy example elevations from `SKILL.md` (such as `13,604 ft` for University Peak) if `post.md` and `--ref-elev-ft` do not list that peak. Always format the bold feature header with a **single** authoritative dual-unit elevation (`**Peak Name (X,XXX ft / X,XXX m)**:`), never hedging with two different elevations in the title.

3. **Features & Line-of-Sight Verification**:
   - **Two-Stage Geometry-First Ordering (Anti-Narrative-Anchoring Rule)**:
     - **Stage 1 (Unbiased Physical & Geometric Discovery — Before Reading `post.md`)**: First run `extract_metadata.py`, view the photo (`read_file`), run `sun-position` and unfiltered `nearby-features <lat> <lon> --radius-km 15.0 --out-json "scratch/<photo_stem>_nearby.json"`, and run your initial `horizon-skyline --out-pano` / `render-topo` pass based purely on visual terrain, solar shadows, and travel vectors. Do **NOT** read `post.md` during Stage 1 (reading directional prose first causes severe narrative confirmation bias).
       - **Exception When EXIF GPS Is Missing (`lat: null, lon: null`)**: If `extract_metadata.py` reports `lat: null` (or emits `"missing_gps_guidance"`) and the photo cannot be tightly interpolated between adjacent geotagged photos taken within `<= 15 minutes` on foot (`prev_photo` is `null` or `elapsed_time_min > 15`), read `post.md` immediately before running `geo_tools.py` to determine whether the photo was taken at a pre-hike camp, shuttle staging trailhead, or highway viewpoint rather than guessing the coordinates of `next_photo`.
     - **Stage 2 (Narrative Cross-Check, Elevation Reconciliation & Draft Placement — Mandatory `post.md` Read)**: Once initial geometric orientation is established, you **MUST** read `post.md` to confirm trail/junction context, test any landmarks mentioned near that segment, reconcile elevations per Step 2, and determine `Suggested Draft Placement` (reading line and narrative paragraph numbers directly from `read_file`'s numbered output of `post.md`—never writing custom paragraph-counting scripts). Physical geometry (solar shadows, travel vector, and 3DEP DEM skyline profiles) **always** overrides directional prose in `post.md`.
   - **Omnidirectional Discovery, Cross-Valley Radius & `VISIBLE` vs. `in_fov`**:
     - Keep Stage 1 `nearby-features <lat> <lon> --radius-km 15.0 --out-json "scratch/<photo_stem>_nearby.json"` **unfiltered** so foreground creeks (`Stream`), waterfalls (`Falls`), glaciers, lakes, and summits are all captured.
     - **Cross-Valley / East-Escarpment Radius (`35.0–40.0 km`)**: Keep `--radius-km 22.0` as the Stage 1 default for `horizon-skyline` inside alpine basins/canyons, but pass `--radius-km 35.0` (or `40.0`) to `horizon-skyline` and `nearby-features` whenever a high-elevation view looks across a major intermountain valley (e.g., across Owens Valley toward the Inyo/White Mountains, `29–40 km` away) so the sweep does not stop on the valley floor (`~22 km`) and miss distant crests or towns (`PopulatedPlace`).
     - `line_of_sight: "VISIBLE"` is azimuth-independent from `(lat, lon)`, whereas `in_fov: false` depends on your `--center-az` guess. Always inspect `top_dominant_360_visible_summits` in `horizon-skyline` (and any `VISIBLE` peak in `post.md`).
   - **Travel-Vector Framing, Switchback Chords & Chronological Bearings**:
     - Test candidate orientations from `prev_photo`, `next_photo`, `prev_hike_stops`, `next_hike_stops`, and `trail_gradient` in order: (1) **Forward** ($\text{bearing} \pm 45^\circ$), (2) **Lateral** ($\text{bearing} \pm 90^\circ$), (3) **Look-backs** ($\text{bearing} + 180^\circ \pm 45^\circ$). On switchbacks/traverses, local trail direction can differ $60^\circ–180^\circ$ from the macro GPS chord; test both when vectors diverge.
     - **Chronological Bearing Rule**: If a landmark's bearing in `nearby-features` lies `~180°` behind your forward walking vector, you have **already passed** it—never describe the photo as "approaching" or "ascending toward" it.
   - **Rigorous Solar Shadow Verification**:
     - Run `sun-position <lat> <lon> "<timestamp>" [--center-az <est_azimuth>]` (and crop subtle foreground shadow casters on even ground via `crop_photo.py` when needed; `camera_azimuth ≈ (shadow_azimuth - image_shadow_clock_offset) % 360`, $\Delta\text{az} = (\text{solar\_azimuth} - \text{camera\_azimuth}) \bmod 360^\circ$):
       - **12 o'clock / straight away (`0°`)** $\rightarrow$ `camera_azimuth ≈ shadow_azimuth` ($\Delta\text{az} \approx 180^\circ$, sun behind).
       - **3 o'clock / left-to-right (`+90°`)** $\rightarrow$ `camera_azimuth ≈ (shadow_azimuth - 90) % 360` ($\Delta\text{az} \approx 270^\circ$, sun on left).
       - **6 o'clock / toward bottom (`180°`)** $\rightarrow$ `camera_azimuth ≈ solar_azimuth` ($\Delta\text{az} \approx 0^\circ$, sun in front / backlit; at solar altitude $<25^\circ$ within $\pm 30^\circ$ of sun, camera-facing trunks/boulders have **dark shadowed front faces with bright rim-lit edges** and shadows point toward the bottom—never confuse rim lighting with cross-lighting!).
       - **9 o'clock / right-to-left (`-90°`)** $\rightarrow$ `camera_azimuth ≈ (shadow_azimuth + 90) % 360` ($\Delta\text{az} \approx 90^\circ$, sun on right).
       - **Diagonal Up-Left (`10–11 o'clock`, sun behind-right $\Delta\text{az} \in [110^\circ, 150^\circ]$) vs. Down-Left (`7–8 o'clock`, dark front faces with rim-lit right/rear edges, sun in front-right $\Delta\text{az} \in [15^\circ, 75^\circ]$)**: Never confuse shadows falling toward the lower-left foreground with `-90°` cross-lighting or behind-right lighting.
       - **Slope Caveat**: Steep 3D slopes ($20^\circ–35^\circ+$) and wide-angle corners rotate 2D shadow clock angles by $\pm 15^\circ–35^\circ$; treat `sun-position` as a $\pm 35^\circ$ octant cue on steep terrain and lock exact azimuth via `horizon-skyline`.
   - **Horizon Skyline, Synthetic DEM Panorama & Geometric Guardrails**:
     - When terrain/skyline is visible, run `horizon-skyline <lat> <lon> --radius-km 22.0 --center-az <est_azimuth> --hfov-deg <hfov_deg> --out-pano "scratch/<photo_stem>_pano.png" --out-json "scratch/<photo_stem>_skyline.json"`.
     - **Close-Up / Ground-Macro Exception (`< 10 ft`)**: If the camera points steeply downward at immediate ground/flora (`< 10 ft`) with **no horizon or midground/background terrain visible**, skip `horizon-skyline` and `calibrate-azimuth` (run only `render-topo --radius-km 1.5` if local trail/creek context is needed).
     - **Stitched Panorama (`-Pano.jpg`) & Steep Canyon Workflows**: When `is_stitched_panorama_candidate: true`, run one wide `horizon-skyline --az-min <min> --az-max <max> --projection cylindrical --out-pano "scratch/<photo_stem>_pano.png" --out-json "scratch/<photo_stem>_skyline.json"` and `crop_photo.py --all-slices 3 --grid`. Inside steep V-shaped canyons where near walls (`0.3–1.5 km`) dominate or azimuth is uncertain, run `render-pano --az-min 0 --az-max 360`.
     - **Visual Alignment with `<photo_stem>_pano.png` & Azimuth Calibration**:
       - View `scratch/<photo_stem>_pano.png` with `read_file` alongside the photo to match distance-shaded bands (`<0.5 km` to `>12 km`), gold basin floors, `[TIP ONLY +0.XX deg]` flags, and blue `Peak ~XXXXft` unnamed highpoints.
       - **Calibration Shift Rules**: Do **not** re-run `calibrate-azimuth` for `< 1.5°` tweaks. Do **not** re-run `horizon-skyline` or re-render `<photo_stem>_pano.png` if `center_azimuth_deg` shifts by **`<= 4°`**. For **`4°–10°`** shifts, run `calibrate-azimuth --center-az <cal_az> --hfov-deg <hfov> --project-bearings "Name1:b1" "Name2:b2"` to update `x_fraction` positions without re-rendering `_pano.png`. Only re-run `horizon-skyline` when off by **`> 10°`**, writing to a distinct filename (`--out-pano "scratch/<photo_stem>_pano_cal.png"`).
     - **2D (`projected_x_fraction` + `clearance_deg` & `GRAZING_TIP_ONLY`) Verification**:
